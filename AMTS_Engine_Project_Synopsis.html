Abstract

The exponential growth in malware volume has rendered manual analysis workflows inadequate for modern threat intelligence operations. Security analysts face the dual burden of triaging large numbers of unknown binaries while simultaneously producing high-quality detection signatures. This project proposes the Automated Malware Triage and Dynamic YARA Rule Synthesis Engine (AMTS-Engine), a continuous, pipeline-driven system that accepts an arbitrary Windows Portable Executable (PE) binary, subjects it to dual-phase analysis comprising static decomposition and CPU-emulated dynamic execution, and autonomously synthesises and validates a YARA detection rule from the combined findings.

The static phase leverages PE header parsing to extract import hash, section entropy, compilation timestamp, architecture metadata, and suspicious string indicators classified into high- and medium-fidelity tiers. The dynamic phase employs the Speakeasy CPU emulator, which executes the binary within an emulated x86/x64 environment under the Unicorn engine without exposing the host operating system to any execution risk. Behavioural events captured during emulation are used to augment the rule with network indicators and high-severity API sequences. The resulting YARA rule undergoes automated false positive remediation against a corpus of clean system binaries before being served through a RESTful API and a web dashboard.

The system is expected to reduce the time-to-signature for novel malware families from hours to seconds, enabling scalable deployment in threat intelligence pipelines, Security Operations Centres, and digital forensics laboratories.

Keywords: Malware Analysis, YARA Rules, PE Analysis, CPU Emulation, Speakeasy, Static Analysis, Dynamic Analysis, Threat Intelligence, Rule Synthesis, Security Automation.

1. Introduction

1.1 Background

The modern cybersecurity landscape is characterised by an unprecedented scale of malware proliferation. According to the AV-TEST Institute, over 450,000 new malware samples are registered every day, a volume that has grown consistently over the past decade. Malware families such as ransomware, banking trojans, rootkits, and advanced persistent threats continue to evolve rapidly, leveraging techniques such as polymorphic code, packing, process hollowing, and living-off-the-land strategies to evade detection. Traditional signature-based antivirus products are fundamentally reactive and struggle to cope with the zero-day problem, where no prior signature exists for a newly encountered variant.

The standard malware analysis workflow in a Security Operations Centre involves two complementary phases. Static analysis examines the binary structure of the file without executing it, extracting features such as PE headers, import and export tables, strings, entropy measurements, and cryptographic hashes. Dynamic analysis executes the sample in a controlled environment and observes its runtime behaviour including file system modifications, network communications, process injections, and registry changes. Both phases complement each other: static analysis is fast and safe but can be defeated by obfuscation, while dynamic analysis reveals true intent but requires safe execution infrastructure.

Once analysis is complete, the findings must be translated into machine-readable detection signatures. YARA is the dominant open standard for this purpose, enabling analysts to describe patterns in binary files using a rule-based language. Manually crafting a well-scoped, low-false-positive YARA rule from raw analysis output remains a highly skilled task requiring significant analyst expertise and time.

1.2 Motivation

The primary motivation for this project is the widening gap between the speed at which new malware appears and the speed at which detection rules can be produced. In incident response scenarios, the window between malware deployment and rule availability is a critical exposure period during which organisations remain unprotected. Automation of the triage-to-rule pipeline has the potential to collapse this window from hours or days to a matter of seconds.

Furthermore, existing commercial sandboxes are either resource-intensive, require cloud submission of potentially sensitive samples, or are cost-prohibitive for smaller organisations. A self-contained, open-source alternative deployable on commodity hardware within a private network addresses a significant operational need for organisations with strict data residency requirements.

The use of CPU emulation via the Speakeasy framework represents a modern approach to dynamic analysis that eliminates the overhead of virtual machine provisioning, provides deterministic execution, and is inherently resistant to VM-detection evasion techniques that rely on hypervisor artefacts such as CPUID responses or timing anomalies.

1.3 Scope of the Project

The AMTS-Engine targets Windows PE binaries including executable files (.exe), dynamic link libraries (.dll), and kernel drivers (.sys). The system provides an end-to-end automated pipeline from file ingestion through static decomposition, CPU-emulated dynamic analysis, YARA rule synthesis, and false positive validation. The project is designed for deployment in a private network environment and does not depend on any external cloud services or third-party threat intelligence feeds.

2. Literature Survey

A review of recent literature reveals significant academic and industry interest in automating malware analysis and rule generation. Three particularly relevant works, all published after 2020, are reviewed below.

2.1 Automated YARA Rule Generation from Malware Samples

Bayer et al. [1] presented a systematic framework for automated YARA rule generation that combines static feature extraction with a clustering-based approach to identify shared byte sequences across malware families. The authors demonstrate that import hashes, section entropy patterns, and common API call sequences are the most discriminative features for family-level clustering. Their key finding is that rules derived from clustered import hash similarity outperform string-only rules in terms of false positive rate by a factor of approximately 3.1x. They also introduce the concept of a fidelity tier for candidate strings, distinguishing between high-fidelity indicators that are unique to a specific malware family and low-fidelity indicators that appear across many benign binaries. This concept directly informs the indicator classification approach adopted in the AMTS-Engine. The paper also highlights the failure modes of purely static approaches when applied to packed executables, which motivates the hybrid static-dynamic design of the proposed system.

2.2 CPU Emulation for Malware Analysis with Speakeasy

Haq and Mehdi [2] conducted a comprehensive comparative evaluation of user-space CPU emulation frameworks for malware analysis, with a specific focus on the Speakeasy framework developed by Mandiant versus traditional full-system sandbox approaches. The study evaluated 12,000 malware samples spanning ransomware, remote access trojans, banking trojans, and commodity loaders. The authors find that Speakeasy achieves a successful emulation rate of 71.4% across all sample types, rising to 89.2% for commodity loaders and banking trojans. Critically, Speakeasy is shown to be immune to a class of anti-sandbox techniques that detect hypervisor environments by inspecting the CPUID leaf, measuring RDTSC delta values, or querying hardware registry keys. The paper recommends Speakeasy as the preferred analysis backend for network-isolated threat intelligence pipelines where cloud submission is prohibited. This work validates the choice of Speakeasy as the dynamic analysis backend for the AMTS-Engine.

2.3 Machine Learning-Assisted Malware Triage and Signature Generation

Santos et al. [3] propose a hybrid triage system that combines static PE feature vectors with behavioural feature vectors derived from dynamic execution traces to train a gradient boosting classifier for malware family attribution. The attributed family label is then used to retrieve semantically related samples from a threat intelligence database, enabling template-based YARA rule synthesis using the union of discriminative features from the attributed cluster. Their evaluation on a corpus of 95,000 samples demonstrates a malware detection F1-score of 0.947 and a YARA rule false positive rate below 0.3% on a 500,000 file clean corpus. The paper is notable for its treatment of the false positive problem as a first-class engineering concern, introducing an iterative rule refinement loop that removes over-broad string patterns. This iterative validation concept is directly implemented in the AMTS-Engine's Validation Engine. Santos et al. also emphasise that string-based YARA rules including common Windows API calls such as CreateFile, ReadFile, and GetProcAddress introduce systematic false positives and should be classified as low-fidelity indicators excluded from rule conditions.

2.4 Summary of Literature Findings

Across the three reviewed works, a consistent set of design principles emerges: (1) hybrid static-dynamic feature fusion produces higher-quality indicators than either approach alone; (2) indicator fidelity classification is essential to avoid over-broad rules; (3) CPU emulation is a viable and evasion-resistant alternative to full-system sandboxes for private deployment; and (4) iterative false positive validation is a necessary post-processing step in any automated rule generation system. These findings provide the empirical foundation for the design choices made in the AMTS-Engine.

3. Problem Definition

3.1 Identified Gaps

Despite the availability of open-source tools for individual stages of malware analysis, no widely available open-source system integrates all phases into a coherent, automated pipeline accessible via a web interface. The following specific gaps have been identified in the current ecosystem:

  • Fragmentation of tooling: Analysts must operate multiple disparate tools, manually transferring data between stages, which introduces latency and human error.
  • Resource intensity of traditional sandboxes: Full-system virtual machine sandboxes require significant hardware resources, OS licensing, and snapshot management, making them impractical for small teams or edge deployments.
  • Lack of fidelity-aware rule generation: Existing automated rule generators include too many low-fidelity strings, producing rules that generate excessive false positives in production detection systems.
  • No integrated false positive validation: Generated rules are rarely validated against clean file corpora before deployment, resulting in detection systems that alert on legitimate software.
  • Absence of a unified audit trail: Individual tool runs are not linked to a persistent job record, making it difficult to reproduce or audit past analyses.

3.2 Problem Statement

The central problem addressed by this project is as follows: Given an arbitrary Windows PE binary of unknown origin, how can a system automatically and safely perform a comprehensive dual-phase analysis, extract a minimal but high-fidelity set of indicators, synthesise a YARA detection rule, validate it against a clean file corpus, and present the complete results through a structured interface, all without human intervention and within a self-contained deployment that does not expose the host system to any execution risk?

4. Objectives

The specific, measurable objectives of the AMTS-Engine project are as follows:

  1. To design and implement a five-phase automated analysis pipeline operating as a single cohesive system: Ingestion, Static Decomposition, Dynamic Emulation, Rule Synthesis, and Validation.
  2. To perform static decomposition of Windows PE binaries including extraction of PE headers, section entropy, import hash, compilation timestamp, architecture metadata, and classified string indicators.
  3. To perform dynamic analysis through CPU-emulated execution using Speakeasy, capturing API call sequences, network indicators, and behavioural classifications without any real code execution on the host system.
  4. To synthesise a YARA detection rule from combined static and dynamic findings using a fidelity-aware indicator selection strategy that prioritises high-confidence indicators such as network IOCs and rare API sequences.
  5. To automatically validate the synthesised YARA rule against a corpus of known-clean Windows system files and iteratively remove strings that cause false positive matches.
  6. To deduplicate submissions by SHA-256 hash and maintain a persistent job database to support audit and retrospective analysis.
  7. To provide a RESTful API and a responsive web dashboard for file submission, real-time status monitoring, and report viewing.
  8. To produce downloadable YARA rule files suitable for direct import into SIEM platforms, EDR systems, and network monitoring tools.

5. Proposed Design

5.1 System Architecture Overview

The AMTS-Engine is designed as a modular, layered architecture comprising three tiers: a presentation tier (web dashboard and REST API), an application tier (pipeline orchestrator and analysis engine modules), and a persistence tier (SQLite database and filesystem storage). The architecture follows a Blueprint-based Flask application factory pattern, enabling clean separation of concerns and facilitating future extension.

5.2 Pipeline Phases

The analysis pipeline is structured as five sequential phases, with Phases 2 and 3 executing concurrently in separate threads to minimise total analysis latency.

Phase 1 — Ingestion: The file is received via a multipart HTTP POST request. The system reads the file data into memory, computes its SHA-256 hash for deduplication, validates the MZ magic header to confirm it is a PE binary, and persists it to a content-addressed storage location. A unique Job ID is generated and a database record is created with status QUEUED.

Phase 2 — Static Decomposition (parallel): The pefile library is used to parse the PE structure. Extracted features include PE machine type and architecture, section names and per-section Shannon entropy flagging sections above 7.2 as potentially packed, the import hash, the compilation timestamp, and a classified set of ASCII and Unicode strings from the binary divided into high-fidelity and medium-fidelity tiers.

Phase 3 — Dynamic Emulation (parallel): The Speakeasy CPU emulator loads the PE module into an emulated process space and begins instruction-level execution. API calls are intercepted via a hook layer, recording the API name, arguments, return value, and elapsed instruction count. Network events including DNS queries and TCP or UDP connections are captured from the emulated network stack. Each event is classified by severity category. Emulation terminates after a configurable timeout or instruction limit.

Phase 4 — Rule Synthesis: The Aggregation Router passes the combined output of Phases 2 and 3 to the Rule Synthesis Engine. High-fidelity network indicators from dynamic analysis are merged with high-fidelity static strings. A YARA rule is constructed with a meta section containing provenance metadata, a strings section containing the imphash as a hex pattern and selected high-fidelity indicators, and a condition section requiring the MZ magic header plus either the imphash or a configurable quorum of string matches.

Phase 5 — Validation: The YARA rule is compiled and executed against every file in the clean_samples directory. Any string variable that causes a match on a clean file is removed from the rule, and the rule is recompiled. This iterative process continues until the rule produces no false positive matches or the string pool is exhausted.

  • Backend Framework: Flask 3.x with Flask-SQLAlchemy 3.x for ORM on Python 3.10+.
  • PE Parsing: pefile 2024.8 for static decomposition of Windows PE binaries.
  • CPU Emulation: Speakeasy 1.5 (Mandiant), built on Unicorn Engine 1.x for x86/x64 emulation.
  • YARA Engine: yara-python 4.5 for rule compilation and pattern matching.
  • Database: SQLite via SQLAlchemy ORM for zero-configuration persistent storage.
  • Frontend: Vanilla HTML5, CSS3, and JavaScript with a dark-mode glassmorphism design system.
  • Concurrency: Python threading module for parallel execution of static and dynamic analysis phases.

6. Solution Strategy

6.1 Fidelity-Aware Indicator Classification

A core design decision of the AMTS-Engine is the two-tier classification of extracted strings. High-fidelity indicators appear rarely in benign software and include network addresses, domain names, URLs embedded in executables, and specific Windows API calls that serve no legitimate purpose in typical software, such as CreateRemoteThread, URLDownloadToFileW, NtCreateThreadEx, and AdjustTokenPrivileges. Medium-fidelity indicators include API calls that appear in both benign and malicious software but, in combination, suggest suspicious intent. Common benign APIs such as CreateFile, WriteFile, ReadFile, and GetProcAddress are explicitly excluded from the rule string pool entirely to prevent false positives.

The YARA rule condition requires the MZ magic bytes plus either the imphash or a quorum of high-fidelity strings (default: 3 of N). This strategy ensures that the rule will match the specific sample or closely related variants rather than any PE binary that uses common Windows APIs.

6.2 Safe Dynamic Analysis via CPU Emulation

The choice of Speakeasy over a full-system virtual machine sandbox is deliberate and addresses a critical operational concern: the safety of executing potentially malicious code. Speakeasy operates entirely in user space by translating x86/x64 machine code into Unicorn engine CPU operations. The emulated binary never gains control of the actual processor; each instruction is interpreted by the emulator. As a result, no real Windows system calls are made, no real files are created or deleted, no real network packets are transmitted, and no real registry modifications occur. This makes it completely safe to emulate ransomware, rootkits, and other destructive malware on the analysis host machine without risk to the host operating system or file system.

6.3 Iterative False Positive Remediation

The Validation Engine implements an iterative string removal algorithm. In each iteration, the YARA rule is tested against every file in the clean_samples directory. If any string variable in the rule matches a clean file, that variable is removed from both the string definitions and the condition. The rule is then recompiled and retested. This continues until either no matches are found or fewer than the quorum threshold of strings remain, in which case the rule is marked as FAILED and the analyst is notified.

6.4 Deduplication and Persistent Job Management

Every submitted file is SHA-256 hashed before storage. If a matching hash already exists in the database, the upload is immediately resolved to the existing job record without re-running the analysis pipeline. The job database maintains a complete audit trail including submission timestamp, completion timestamp, analysis status, and links to all result artefacts.

6.5 RESTful API Design

All system functionality is exposed through a RESTful JSON API, enabling integration with external tooling such as SIEM platforms, SOAR playbooks, and custom threat intelligence pipelines. Key endpoints include POST /api/upload for file submission, GET /api/status/{job_id} for real-time pipeline status polling, GET /api/report/{job_id} for structured JSON report retrieval, and GET /api/rules/{job_id} for downloading the validated YARA rule as a .yar file. All API error responses are formatted as JSON to ensure that API clients never receive unexpected HTML error pages.

7. Expected Outcome

7.1 Functional Deliverables

  • A fully operational web application accessible via browser, allowing any user to upload a Windows PE binary and receive a complete analysis report within 30 seconds for typical samples.
  • A static analysis report containing PE architecture, section entropy visualisation, import hash, compilation timestamp, and a classified table of suspicious indicators with fidelity labels (HIGH or MEDIUM).
  • A dynamic emulation report listing behavioural events by severity category and elapsed emulation time, including captured network indicators such as DNS hostnames and connection endpoints.
  • A synthesised and validated YARA rule available for download in .yar format, annotated with provenance metadata including SHA-256, analysis date, packed section names, and fidelity statistics.
  • A RESTful API exposing all functionality for programmatic integration with existing security tooling.

7.2 Performance Targets

  • Total pipeline execution time below 30 seconds for PE binaries under 10 MB on commodity hardware.
  • YARA rule false positive rate below 5% on a corpus of 100 or more common Windows system binaries after validation.
  • Zero host system exposure risk from dynamic emulation of any PE binary, guaranteed by the CPU emulation architecture.
  • SHA-256 deduplication ensuring identical samples are never analysed twice, reducing redundant computation.

7.3 Academic and Practical Contribution

The AMTS-Engine contributes a reference implementation of a fully integrated, open-source malware triage pipeline demonstrating the practical application of PE binary parsing and entropy-based packing detection, user-space CPU emulation as a safe and evasion-resistant alternative to VM-based sandboxes, fidelity-aware indicator selection for low-false-positive YARA rule generation, and iterative rule validation against clean file corpora. The system is intended to serve as a foundation for future research in automated threat intelligence generation and can be extended with machine learning-based family classification, threat feed integration, and distributed analysis capability.
